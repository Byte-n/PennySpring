# 组件规范巡检问题修复 Agent 提示词

## 目标

读取 `docs/issues/` 下的巡检报告，逐个组件修复其中列出的不合规问题。每个组件的修复任务串行委派给独立 subagent，主 agent 负责进度汇报与最终收尾。

已处理进度在 `.claude/prompts/ps.md` 中

---

## 主 Agent 流程

### 1. 扫描报告

```
读取 docs/issues/*.md，过滤出"状态：不通过"的报告。
按文件名排序，生成待处理组件列表 components[]。
输出：共发现 n 个组件需要修复。
```

### 2. 串行调度 Subagent

对 `components[]` 中的每个组件，按顺序执行：

```
for i, component in enumerate(components):
    汇报进度："[i+1/n] 开始修复 {component.name}..."
    调用 subagent（见下方 subagent 提示词），传入：
      - 报告文件路径
      - 组件名
    等待 subagent 完成
    汇报结果："[i+1/n] {component.name} 修复完成（通过/失败）"
```

### 3. 进度汇报格式

每处理一个组件，主 agent 必须输出一行进度：

```
[3/15] Avatar — 修复完成 ✓
[3/15] Avatar — 修复失败 ✗（原因：xxx）
```

并同步更新 `.claude/prompts/ps.md`

### 4. 全部完成后

- 汇总结果：成功 n 个，失败 n 个
- 若有失败项，列出失败组件与原因
- 执行 `yarn run lint` 与 `yarn run typecheck` 验证整体一致性

---

## Subagent 提示词

> 以下内容作为 prompt 传入每次 subagent 调用，需替换 `{component}` 和 `{report_path}` 为实际值。

```
你是一个组件修复 agent。你的任务是根据巡检报告修复 PennySpring 项目中 {component} 组件的不合规问题。

## 输入

- 报告路径：{report_path}
- 组件名：{component}

## 工作流程

### 第一步：理解问题

1. 读取报告文件，提取所有"问题列表"中的条目。
2. 对每个问题，理解：
   - 违反了哪条规范
   - 当前代码是什么样的（报告中的"位置"字段指向具体文件和行号）
   - 报告推荐的纠正方案是什么

### 第二步：阅读现状

1. 读取报告中"位置"指向的源文件，理解当前实现。
2. 读取组件的完整源码目录 `packages/pennyspring-ui/src/{component}/`。
3. 找到所有使用该组件的其他文件（grep 组件名在 `src/`、`examples/`、`__tests__/` 中的引用）。

### 第三步：TDD — 编写失败测试（RED）

1. 在组件的 `__tests__/` 目录下，为每个问题编写测试用例。
2. 测试必须：
   - 按 AAA（Arrange-Act-Assert）组织
   - 测试名描述被验证的行为，不是实现细节
   - 针对报告中描述的"不符合点"设计断言
3. 运行测试，确认测试失败（RED 阶段）。

### 第四步：TDD — 最小实现使测试通过（GREEN）

1. 按报告"推荐纠正方案"修改组件源码。
2. 修改必须：
   - 遵循 CLAUDE.md 中的样式约束（createUseSheetStyle、token 驱动）
   - 遵循 component-visual-layout.md 的规范
   - 保持不可变性
   - 不引入无关改动
3. 运行测试，确认新增测试通过，存量测试不回归。

### 第五步：TDD — 重构（REFACTOR）

1. 在测试全绿的前提下，清理实现代码。
2. 运行测试确认无回归。

### 第六步：更新引用

1. 如果组件的 props 接口发生变化，更新所有使用该组件的文件。
2. 更新 `examples/` 下的预览示例，确保示例反映修复后的正确用法。
3. 如果有 `types.ts` 变更，确保所有导入方同步。

### 第七步：收尾验证

1. 运行 `yarn workspace @pennyspring/ui test`，确认全部通过。
2. 运行 `yarn workspace @pennyspring/ui typecheck`，确认无类型错误。
3. 运行 `yarn workspace @pennyspring/ui lint`，确认无 lint 错误。

### 第八步：回写报告

1. 根据修复结果，更新报告文件：
   - 在每个已修复的问题标题后添加 `✅`
   - 在每个跳过的问题标题后添加 `⏭️（原因：xxx）`
   - 在每个失败的问题标题后添加 `❌（原因：xxx）`
2. 更新报告顶部的"状态"字段：
   - 全部修复 → `状态：通过`
   - 部分修复 → `状态：部分通过`
   - 全部失败 → `状态：不通过`

## 约束

- 不修改与当前问题无关的代码。
- 不修改与当前问题无关的代码。
- 如果报告中的"推荐纠正方案"不可行（会导致回归或其他问题），记录原因并跳过该问题，在输出中说明。
- 所有样式必须通过 token 驱动，禁止硬编码颜色、数字字面量（0、flex:1、百分比除外）。
- 共享组件修改后必须检查其他组件对它的依赖。

## 输出格式

修复完成后，输出简要总结：

```
组件：{component}
问题数：{n}
修复：{n} 个
跳过：{n} 个（原因：xxx）
测试：新增 {n}，全部通过
状态：通过 / 部分通过 / 失败
